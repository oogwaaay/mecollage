无后端策略对比（需要维护者拍板）

站点是纯静态（Vercel 静态托管、无后端）。三个选项的取舍不同，推荐 A，B 作为需要更好投递时的备选。

A · mailto fallback 推荐

表单在浏览器里拼好 mailto:hello@mecollage.top?subject=…&body=…，交给用户自己的邮件客户端发送。

  • 优点：零后端、零第三方、零费用；与「照片不出设备/无账号」的隐私叙事一致；无 secret 可泄露。
  • 代价：依赖用户有邮件客户端；无法保证送达/回执；邮箱地址必须公开（会有垃圾邮件）；无法统计。
  • 缓解：同时显示可复制地址；提交后给明确确认面板；不发营销邮件。
改动：contact.html ×5 语言 + JS 拼 mailto + i18n 键；无需账户/平台操作。

B · 第三方表单服务 备选

Formspree / Netlify Forms / Tally 等接收 POST 并转发到邮箱。

  • 优点：真正的“发送成功”回执；服务端反垃圾；无需自建后端；免费额度通常够小站。
  • 代价：新增外部请求与数据处理者 → 隐私政策需写明；需维护者注册账户/配置 endpoint（H8 账户级，AI 不能代办）；免费额度/服务条款变化风险。
  • 缓解：只收集必要字段；表单页隐私提示；选 EU 区域服务；保留邮件兜底。
改动：同上 + endpoint 配置 + Privacy Policy 更新 + 第三方服务账户（需维护者操作）。

C · 自建后端 不推荐（本轮）

Vercel Function / Worker + 邮件 API（Resend/Mailgun）接收表单。

  • 优点：完全可控、可做反垃圾与工单系统。
  • 代价：引入服务端代码/密钥/运维/监控；与当前“纯静态、无密钥、无账户”模型冲突；需要新的安全评审与滥用预算。
  • 结论：等真的有日均 50+ 反馈、或需要工单流程时再考虑（R3+）。
改动：新增 serverless + 密钥管理 + CSP/限流 + 监控，超出本轮 R2 原型范围。

5 语言 / i18n 要求（不能只做英文）

contact 页在 root + es/ ja/ tw/ zh/ 共 5 套手写副本；表单字段、错误、成功、隐私提示必须全部走 i18n 键（L-02/L-23）。英文为源语言，其余 4 份同批提交：

contact.form.name · contact.form.email · contact.form.topic · contact.form.message · contact.form.submit · contact.form.privacy · contact.form.error.name · contact.form.error.email · contact.form.error.message · contact.form.success.mailto · contact.form.success.sent · contact.form.copy · contact.topic.*（5 个选项）· contact.expect.*

语言切换仍是真实 <a href> 锚点（L-09/L-24），不改 URL 结构；H1/meta/title 保持现有多语言版本（不因加表单而改 SEO 主题）。

D1
加表单，还是改名 Support？审计 P2-3 的两个选项。本原型选择“加表单 + 保留 GitHub Issues 主路径”；若维护者暂无收件邮箱/不想公开地址，则退回“改名 Support + 写清响应渠道”，不加表单。
D2
收件邮箱是否存在、是否公开？mailto 方案必须公开一个可达邮箱（如 hello@mecollage.top）。需维护者确认已有邮箱/别名、是否接受公开后的垃圾邮件量。
D3
第三方服务合规若选 B：需在 Privacy Policy 写明数据处理器、保留时长；注册服务账户属于账户级操作（H8），需维护者执行/授权并留证据。
D4
可访问性与反滥用label/aria-describedby/aria-live 错误汇总、focus 回错误摘要、44px 触控；若选 B 加 honeypot + 服务端限流，不在前端做“看起来像验证”的假验证码。
